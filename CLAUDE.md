# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

ASI (Argentina Seguridad Integral) is a prototype for a private security company's field-supervision app, built to the requirements of **PRD 1 — Panel de Supervisión** (rev. 22/04/2026). Three parts:

- `asi_prototype.html` — a single-file React 18 app (no build step; React, ReactDOM and Babel are loaded from CDN via `<script>` tags, styled with the Tailwind CDN build plus the inline "Apple institucional" design system — see DESIGN.md). Open it directly in a browser to run it.
- `server.js` — an Express + PostgreSQL REST API (JWT auth + RBAC) that the prototype connects to at runtime.
- `schema.sql` — idempotent schema + seed data. Re-runnable at any time with `psql asi -f schema.sql`.
- `android/` — a Capacitor-wrapped native Android shell around the same `asi_prototype.html` (see **Android build** below). `asi_prototype.html` remains the single source of truth; the native project just loads it in a WebView.
- `mobile/` — the **native app** (React Native + Expo SDK 57, TypeScript, Expo Router), chosen after researching what MercadoLibre/PedidosYa/Rappi ship (native UI, not a WebView). It talks to the same `server.js` API with the same request bodies as the web, and is the long-term replacement for the Capacitor shell. See **Native app (`mobile/`)** below.
- `assets/brand/` — the official ASI logo (lockup navy/white, emblem) taken from argentinaseguridad.com.ar. The web embeds them as base64 (`LOGO_ASI`, `EMBLEMA_ASI`); `mobile/assets/brand/` holds copies.

`PLANTILLAS_CHECKLIST.md` and `PREGUNTAS_CLIENTE_CHECKLIST.md` are client-meeting handouts (in Spanish) documenting the five checklist templates and the questions used to relevar each real objetivo's per-item differences — read them for the *business* rationale behind `checklist_items.tipos_objetivo` and `objetivo_checklist` before changing checklist logic.

`PRODUCT.md` and `DESIGN.md` (plus the machine-readable `.impeccable/design.json`) are the design contract produced by the `impeccable` skill in `.claude/skills/`: PRODUCT.md records who the users are and the confirmed field conditions (variable outdoor light, one-handed/gloved use, unreliable connectivity) that justify the UI's touch targets and contrast; DESIGN.md + design.json record the shipped token palette and component rules. `.claude/settings.json` wires an `impeccable` hook that runs on every Edit/Write and again on Stop, so UI edits get design-checked automatically — read DESIGN.md before changing tokens, spacing or component styling rather than inventing new values.

`README.md` is an unedited GitHub Desktop placeholder — ignore it.

There is no test suite. Dependencies are declared in `package.json` (`npm install` before running the server).

## Running things

Full local stack, in order: `brew services start postgresql@16` → `npm start` (port 3000) → `python3 -m http.server 5500` → open `http://localhost:5500/asi_prototype.html` and point `ApiConfigBar` at `http://localhost:3000`. Skipping the last step is fine — the app runs in demo mode off the `SEED_*` constants.

- **Frontend**: serve it over HTTP so CORS works — `python3 -m http.server 5500`, then open `http://localhost:5500/asi_prototype.html`. Opening the file directly via `file://` also works in demo mode, but the browser will block API calls.
  - To test real browser geolocation (geocerca checks), plain HTTP isn't enough — Chrome only grants `navigator.geolocation` on secure contexts. Use `python3 serve_https.py` instead, which serves the same directory over HTTPS on port 5500 using the self-signed cert in `certs/` (gitignored; regenerate with your own if missing).
- **Backend**: `node server.js` (or `npm start`). Loads env vars from a local `.env` via `dotenv` (gitignored — copy `.env.example`). It refuses to start unless these env vars are set: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `JWT_SECRET` (min 32 chars). Optional: `PORT` (default 3000), `CORS_ORIGIN` (comma-separated, default `http://localhost:5500`).
- **Database**: PostgreSQL 16 via Homebrew (`brew services start postgresql@16`), database `asi`. `psql` lives at `/opt/homebrew/opt/postgresql@16/bin` and is not on the default PATH.
- **Android build**: `asi_prototype.html` is the source of truth; it is *not* edited inside `www/` or `android/` directly.
  1. `npm run cap:sync` — copies `asi_prototype.html` → `www/index.html` (`cap:sync-web`), then runs `npx cap sync android` to copy the web assets into `android/app/src/main/assets/public` and update native plugins. Run this after every change to `asi_prototype.html` that you want reflected in the Android build.
  2. `npm run cap:open` — opens the native project in Android Studio (`npx cap open android`). Requires Android Studio + a JDK on PATH; neither is assumed to be installed.
  3. CLI build without Android Studio: JDK 21 (`brew install openjdk@21`, add `/opt/homebrew/opt/openjdk@21/bin` to PATH) + Android SDK command-line tools (`brew install --cask android-commandlinetools`, then `sdkmanager --sdk_root=/opt/homebrew/share/android-commandlinetools "platform-tools" "platforms;android-34" "build-tools;34.0.0"`). `android/local.properties` (gitignored) must point `sdk.dir` at the SDK root. Then `cd android && ./gradlew assembleDebug` produces `android/app/build/outputs/apk/debug/app-debug.apk`.
  4. `www/` is gitignored (regenerated by `cap:sync-web`); `android/` is committed since it carries native customizations (manifest permissions, network security config), except `android/local.properties` which is machine-specific and gitignored.
  5. The API base URL is still set at runtime via `ApiConfigBar`, same as the web build — on an emulator, `localhost` from the host machine is reachable at `10.0.2.2`; on a physical device it needs the backend's real LAN/deployed URL. `android/app/src/main/res/xml/network_security_config.xml` only whitelists cleartext HTTP for `10.0.2.2`/`localhost`/`127.0.0.1` — add any other dev host there, and don't widen it to a blanket `usesCleartextTraffic` in production.
  6. `AndroidManifest.xml` declares `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` (geocerca) and `CAMERA` (evidence capture via `<input capture="environment">`); `MainActivity` extends Capacitor's `BridgeActivity`, which prompts for the geolocation runtime permission automatically — no plugin code needed for `navigator.geolocation` to work inside the WebView.
  7. **Emulator GPU acceleration is critical** — `avdmanager create avd` defaults to `hw.gpu.enabled=no` in `~/.android/avd/<name>.avd/config.ini`, which forces SwiftShader software rendering and makes the UI crawl (<5fps). Set `hw.gpu.enabled=yes` / `hw.gpu.mode=host` in that config.ini (or launch with `emulator -avd <name> -gpu host`) before judging any performance issue as an app bug — check `/tmp/emulator.log` for `gles_mode_selected:host` (good) vs `gles_mode_selected:swangle` (software, bad).
  8. `PhoneFrame` (in `asi_prototype.html`) renders a fake phone bezel + status bar for the desktop-browser preview only; it detects `window.Capacitor?.isNativePlatform()` and skips that chrome entirely on native builds, filling the real screen edge-to-edge instead.
- **Test users** (seeded): `supervisor`/`supervisor123`, `admin`/`admin123`, `dueno`/`dueno123`. Test vigilador legajos: 1024, 1087, 1153, 1201.
- The frontend and backend are decoupled: the prototype works fully in **demo mode** against in-memory seed constants (`SEED_*`), and switches to live data once a URL is connected via `ApiConfigBar`. Every panel must keep working in both modes — this fallback is deliberate.

## Verifying changes

Drive the app in a real browser (Chrome automation tools are available). Note that synthetic clicks from the automation tool do not always register on `clay-btn` elements (the class name survived the redesign); clicking programmatically via `element.click()` in the page context is reliable. After a supervisor round, confirm persistence with `psql asi -c "SELECT ... FROM rondas_actas"` — the acta, per-guard signatures, checklist answers, evidence photos and tickets should all appear in one transaction.

## Architecture

### Frontend (`asi_prototype.html`)

Everything lives in one `<script type="text/babel">` block, rendered into `#root` via `ReactDOM.createRoot`. File order: design tokens/CSS → seed data → logo constants → `Icon` + UI primitives (still named `Clay`, `.clay*` for continuity) → `AppContext` → login/shell → supervisor steps → admin/owner panels → root.

- **Design system: "Apple institucional"** (replaced claymorphism in Sep 2026 — the owner found it unserious). Flat white surfaces on `#F4F6FA` separated by 1px lines, a single brand color (the logo's navy `#16256E`/`#1F327C`), Barlow typography, ≥44px touch targets and 56–58px primary actions. Defined once in the `<style>` block and the inline `tailwind.config`; the legacy class/tone names (`.clay*`, `brand`/`plum`/`tang`/`aqua`) were kept but remapped to the new tokens, and a `#root .text-[Npx]`/`.font-black` override block raises small sizes and lowers weights for field legibility — so old markup renders in the new system. Semantic tones `good`/`warn`/`bad` are reserved for the Likert B/R/M and real states. DESIGN.md is the source of truth; the reference mockups live in the "ASI — Login institucional" canvas artifact. **Never use emojis as icons** — all iconography goes through the `Icon` component, which renders lucide-style SVG paths from the `ICON_PATHS` map. Add new icons there rather than inlining `<svg>`.
- **`AppContext` / `AppProvider`** — the single source of truth: local mirror state (`rondasGuardadas`, `ticketsActivos`, `liveFeed`, `visitasPorObj`, KPIs via `useMemo`), the offline FIFO queue (`queue`/`offline`/`syncing`, with automatic 60s retry per PRD §10), the API layer (`apiFetch`, `conectarApi`, `cargarCatalogos`), and the catalogs (`objetivos`, `vigiladores`, `secciones`, `checklistDefs`, `observaciones`) which start as `SEED_*` and are replaced by `GET /api/inicializar` once authenticated. **Catalogs load on `apiToken` change, not on connect** — the endpoint requires auth.
- **Offline queue is persisted, not just in-memory** — `abrirQueueDB` / `leerQueuePersistida` / `guardarQueuePersistida` mirror the FIFO queue into IndexedDB (`asi_offline_queue`), so actas queued offline survive a refresh or tab close. IndexedDB and *not* `localStorage` deliberately: base64 evidence photos are multi-MB and blow past the localStorage quota. Every failure path degrades to an in-memory-only queue with a `console.warn` rather than throwing.
- **Role-based routing** — `AppInner` renders `LoginScreen`, `SupervisorPanel`, `AdminPanel` or `OwnerPanel` based on `currentUser.rol`. No router; a plain conditional inside `PhoneFrame`. `AppInner` also computes `wide = rol is admin or dueno`, which puts only those two panels into the desktop/tablet layout (`device-wrap--wide`, phone bezel and status bar hidden). Supervisor and login stay inside the phone frame at any viewport — that is intentional (the supervisor is always on a phone in the field, per PRODUCT.md), so don't "fix" it by making them responsive too.
- **Supervisor flow** — a 5-step wizard (`Step1`–`Step5`) plus the generated acta (`ActaGenerada`): objetivo + geocerca → multiple vigiladores → checklist → photo evidence → per-guard signatures. The wizard's working state is a single `rd` object (objetivo, tipo, respuestas keyed by item id, fotos, firmas keyed by vigilador id). `guardarRonda` builds the acta via `construirActa` (which derives each ticket's responsible area from the *selected observation's* area, falling back to the checklist item's) and either commits locally + POSTs to `/api/rondas`, or enqueues when offline.
- **Checklist is data-driven, two layers deep** — `checklistDefs` items carry `tipos_objetivo`, giving every objetivo a checklist template based on its `subtipo` (5 templates — industria/planta, barrio multipuesto/unipersonal, local comercial, empresa/oficinas; documented client-facing in `PLANTILLAS_CHECKLIST.md`). On top of that, `objetivo_checklist` rows let a specific objetivo add or remove individual items from its template's default set. `resolverChecklist(objetivo, defs, ajustes)` merges the two: an explicit `ajustes` row wins (`incluido` true/false), otherwise the template's `tipos_objetivo` membership decides. This is what lets two "local comercial" objetivos end up with different item counts without duplicating the template. Long-press or the info button reveals `criterio_completo`.
- **Evidence photos** — `estamparFoto` draws the image to a canvas and burns in a date/time/GPS/supervisor watermark before the data URL is stored. The watermark is applied at capture time and is not editable afterwards.
- **Graceful degradation** is deliberate: every panel works against the `SEED_*` constants with no backend, and transparently switches to live data once `apiStatus === "connected"`. Preserve this when modifying panels.

### Backend (`server.js`)

Single-file Express API secured with JWT auth + RBAC, talking to PostgreSQL via `pg.Pool`.

- **Auth**: `POST /api/login` verifies bcrypt password hashes against `usuarios` and issues a JWT (8h expiry per PRD §10) containing `{ id, nombre, rol }`. Login always runs `bcrypt.compare` even for unknown usernames (timing-attack / user-enumeration mitigation). Its request body is `{ username, password }` — those two field names are English even though the rest of the API is Spanish; sending `usuario` gets a 400.
- **`requireAuth`** validates the `Authorization: Bearer <token>` header and attaches `req.user`. **`requireRole(...roles)`** gates endpoints by `req.user.rol` (`supervisor`, `admin`, `dueno`). Roles map 1:1 to the frontend's three panels.
- **Endpoints**: `GET /api/inicializar` (auth-only — objetivos with current-month visit counts, vigiladores, checklist sections/items, observation catalog), `POST /api/rondas` (supervisor-only), `GET /api/vigilador/:legajo` (supervisor — full profile + historial + sanciones + incidencias), `GET /api/tickets` (admin/dueno, paginated + filterable by estado/objetivo/area), `PATCH /api/tickets/:id/resolver` (admin), `GET /api/kpis` and `GET /api/actividad` (admin/dueno). `GET /` is an unauthenticated health check that echoes the endpoint list — `curl -s localhost:3000/` is the quickest way to confirm the API is up.
- **`POST /api/rondas` is one transaction**: `rondas_actas` → per-guard `ronda_vigiladores` (each with its own signature or `nego_firmar`) → `checklist_respuestas` → `evidencias_fotos` → `tickets_incidencias`, inside a single `BEGIN`/`COMMIT`/`ROLLBACK`. It accepts `vigiladores: [{id, firma_base64, nego_firmar}]` and still tolerates the legacy `vigilador_ids` array. It rejects an acta with no signature and no recorded refusal.
- **Codes are generated after insert** (`ACTA-YYYYMMDD-<id>`, `INC-YYYYMM-<id>`) using the DB-assigned row id, specifically to avoid race conditions from pre-generating sequential codes.
- **Security middleware order**: `helmet()` → CORS allowlist (`CORS_ORIGIN` env) → general rate limit (200 req/15min/IP) → stricter `loginLimiter` (10 req/15min) on `/api/login`. The JSON body limit is 25mb because evidence photos travel as base64.
- **Input validation at the endpoint boundary** — the shared helpers `isPositiveInt`, `isString(v, min, max)`, `isValidLat`, `isValidLng`, `isValidDate`, `isValidPrecision` are applied before any SQL runs, and reject with a 400 carrying a Spanish `error` message. New endpoints (and new fields on `POST /api/rondas`) are expected to validate the same way rather than relying only on the DB's CHECK constraints.
- **Configuration lives in the database, not in code**: `checklist_secciones`, `checklist_items` (with `tipos_objetivo[]`), `objetivo_checklist` (per-objetivo item add/remove) and `observaciones_catalogo` drive what the supervisor sees. To change a checklist, edit `schema.sql` and re-run it — do not hardcode items in the API. Keep the `SEED_*` constants in the HTML roughly in sync so demo mode matches.

### Database (`schema.sql`)

`schema.sql` is the only migration mechanism — there is no migration tool, so the whole file must stay safely re-runnable against an existing populated database. Follow the established patterns instead of editing table definitions in place:

- New columns go in as `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` **after** the original `CREATE TABLE IF NOT EXISTS`, never by editing the `CREATE TABLE` body (existing databases would never see the change).
- Constraints are added inside `DO $$ BEGIN ... EXCEPTION WHEN duplicate_table OR duplicate_object THEN NULL; END $$;` blocks, since `ADD CONSTRAINT` has no `IF NOT EXISTS`.
- Seed data uses `ON CONFLICT (<natural key>) DO UPDATE SET ...` so re-running updates rows rather than duplicating them — that natural key (`objetivos.nombre`, `checklist_items.titulo_corto`, `vigiladores.legajo`, `observaciones_catalogo.texto`, …) is what makes the seed idempotent, so keep the corresponding UNIQUE constraint in place.
- Enum-like domains live in CHECK constraints (`rol`, `objetivos.tipo`/`subtipo`/`modalidad`, `valoracion IN ('B','R','M')`, `tickets.estado`). Adding a new value means editing the CHECK — and, since the DB is the config source, the matching `SEED_*` constant in the HTML.

## Language

Code comments, log messages, and API response fields are in Spanish (Argentina) — match this convention when editing `server.js` or `asi_prototype.html`.

### Native app (`mobile/`)

- **Stack**: Expo SDK 57 / React Native 0.86 (New Architecture), Expo Router (`src/app/`, file-based), Reanimated 4 + Gesture Handler, `expo-sqlite`, `expo-location`, `expo-image-picker`, `expo-secure-store`, `@react-native-community/netinfo`, `react-native-svg`, `react-native-view-shot`, Barlow via `@expo-google-fonts`. Read `mobile/AGENTS.md`: Expo APIs change every SDK — check the versioned docs, and install with `npx expo install`, never plain `npm install` (plain npm hits an ERESOLVE on an optional `react-dom` peer).
- **Same contract as the web**: `src/domain/acta.ts` builds the exact `POST /api/rondas` body `enviarActaApi` builds in the HTML (tickets per R/M item routed by the observation's area, plus one RRHH ticket per refusal to sign); `src/domain/checklist.ts` is a port of `resolverChecklist`. Change both sides together.
- **Demo mode**: without a server URL (set on the "Servidor" screen) it runs on `src/data/seed.ts`, which is **generated** from the HTML's `SEED_*` by `npm run seed` — don't hand-edit it.
- **Offline**: `src/state/outbox.ts` is a SQLite outbox. Actas are queued when offline (or when the network drops mid-send), photos stay as files (base64 is read only when sending), and `session.tsx` retries on reconnect and every 60s. A 4xx from the server (e.g. outside the geofence) is shown to the user instead of queued. The "Simular sin señal" switch on the Servidor screen forces offline for demos.
- **Evidence**: photos are watermarked (date/time/GPS/supervisor) at capture by compositing and `captureRef`-ing the view — the stamp is burned into the saved JPEG, same guarantee as `estamparFoto`.
- **Build**: `cd mobile && npx tsc --noEmit && npx expo-doctor`, then `npx expo prebuild --platform android` (generates the gitignored `mobile/android/`; needs `mobile/android/local.properties` with `sdk.dir`) and `cd android && ./gradlew assembleRelease` with JDK 21 → `mobile/android/app/build/outputs/apk/release/app-release.apk` (signed with the ASI key, see **Signing** below). **Build speed on this 8 GB M1**: the first full build of all 4 ABIs swapped the machine for 40+ min (and killed the emulator). `expo-build-properties` now limits `buildArchs` to `arm64-v8a` (every current phone and the Apple-Silicon emulator; add `x86_64` only if you need an x86 emulator) and `mobile/plugins/withGradleSpeed.js` sets `-Xmx3g`/Metaspace 1g, `workers.max=4` and the build cache — keep both, and close Docker/Colima before a clean build. For iterating, `npx expo run:android --variant debugOptimized --device` is faster than `assembleRelease`. Release builds block cleartext HTTP except for the hosts whitelisted by `mobile/plugins/withRedLocal.js` (`10.0.2.2`, `localhost`, `127.0.0.1`, `*.ts.net` for the Tailscale server) — on an emulator the host API is `http://10.0.2.2:3000`; any other host needs HTTPS or an entry in that plugin, never a blanket `usesCleartextTraffic`.

- **Fast workflow (`mobile/package.json` scripts)** — pick the cheapest step for what changed:
  - JS/TS only → `npm run dev:android` (debugOptimized + Metro: changes hot-reload on the device, no APK) or `npm run apk:prueba` (release, arm64 only, ~40 s incremental).
  - App config (icons, permissions, plugins, `app.json`) → `npm run nativo:regenerar` then build. Run it as a clean regenerate: a plain `expo prebuild` over an existing `android/` once died half-way with `ENOTEMPTY` and left `android/` broken.
  - APK to hand out → `npm run apk:entrega` (armeabi-v7a + arm64-v8a, ~11 min clean). Keep both ABIs: many low-end phones (Moto E, Samsung A0x, Android Go) run 32-bit Android and won't install an arm64-only APK.
- **Device-matrix testing**: `minSdk` is 24 (Android 7.0, the RN 0.86 floor). Emulator scripts used for the Android 7/10/14/16 matrix lived in `/tmp` (`probar.sh` measures cold start, PSS memory, `gfxinfo` jank and crashes; `lote.sh` downloads an image, boots it headless, tests, deletes it). Disk is tight on this Mac — emulators default to a 6 GB data partition; pass `-partition-size 2048` and set `disk.dataPartition.size` (the stock key is written with spaces around `=`). When driving the emulator with `adb` from a script, redirect `adb`'s stdin from `/dev/null` or it swallows the rest of the script.

### Signing (both APKs)

- **One ASI key for every machine**: `~/ASI-Firma/asi-release.jks` (PKCS12, alias `asi`, RSA 4096), created 2026-10-01. It lives outside the repo; `*.jks`/`*.keystore` are gitignored. Gradle reads it from `~/.gradle/gradle.properties` (`ASI_STORE_FILE`, `ASI_STORE_PASSWORD`, `ASI_KEY_ALIAS`, `ASI_KEY_PASSWORD`; the ready-to-copy block is `~/ASI-Firma/gradle.properties`). Every teammate who builds needs the same `.jks` + those four lines — share them privately, never via git or chat.
- Wired in `android/app/build.gradle` (Capacitor, by hand) and `mobile/plugins/withFirmaAsi.js` (native, injected at prebuild). Both debug and release use it when present and fall back to the local debug key otherwise. Before this, the Capacitor APK was signed with each machine's own `~/.android/debug.keystore`, which is why installing a teammate's build over another one failed with "No se instaló la app / ya hay una versión anterior" (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`).
- `versionCode` is automatic in both apps (minutes since 2026-01-01), so every build is a valid update of the previous one.
- **Losing this key means installed apps can never be updated again** (and it will be the Play Store upload key). Keep a backup outside this Mac.
